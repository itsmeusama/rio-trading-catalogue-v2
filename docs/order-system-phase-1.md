# Permanent Order System — Phase 1 Contract

This document fixes the data and API contract for the planned Google Apps Script
order backend. Phase 1 is specification only: it does not change the current
frontend, create spreadsheet tabs, deploy Apps Script, or remove EmailJS.

## Confirmed business decisions

- Keep the existing product spreadsheet as the single workbook.
- Keep the existing product catalogue tab unchanged.
- Add separate `Orders` and `Order Items` tabs during backend setup.
- Save every accepted order before attempting to send its email.
- Send the order email only to `riotraders87@gmail.com` initially.
- The same Google account owns and authorises the Apps Script deployment.
- Attach a PDF to the owner email, but do not store PDFs in Google Drive.
- Do not send a customer copy initially.
- Use GBP and do not calculate VAT in this version.
- Treat stock as informational; accepting an order does not reserve or deduct stock.
- Use `Open`, `Delivered`, and `Cancelled` as order statuses.
- Use `Pending`, `Sent`, and `Failed` as email statuses.

## Workbook structure

The existing Google Sheets file will contain three independent tabs:

```text
Rio_Trading_Product_Sheet
├── rio_trading_products_template  (existing catalogue; sheet gid 1147224303)
├── Orders        (one row per accepted order)
└── Order Items   (one row per product line)
```

The workbook is now a native Google Sheet with spreadsheet ID
`1pDmFNcjy9kBjF0qjH-SoOWXJqbajEqZgsSVdiRTAYtk`. Its published catalogue CSV is
the production feed configured in `script.js`.

The Phase 2 setup function will create the two order tabs and their headers if
they do not already exist. It must never overwrite existing order rows.

## `Orders` schema

| Column | Sheet type | Purpose |
| --- | --- | --- |
| `order_ref` | Text | Permanent reference generated by Apps Script, using `ORD-YYYYMMDD-XXXXX`. |
| `submission_id` | Text | Browser-generated UUID used to prevent duplicate orders. Must be unique. |
| `created_at` | Date/time | Server timestamp in the `Europe/London` timezone. |
| `shop_name` | Text | Customer shop or business name. |
| `contact_name` | Text | Customer contact person. |
| `phone` | Text | Customer phone number, stored as text to preserve leading zeroes. |
| `customer_email` | Text | Customer email for the permanent record; not an email recipient initially. |
| `notes` | Text | Optional order or delivery instructions. |
| `currency` | Text | Always `GBP` in this version. |
| `item_count` | Number | Sum of all product quantities in the order. |
| `gross_subtotal` | Currency | Total before item-level discounts. |
| `item_discount_amount` | Currency | Combined value of all item-level discounts. |
| `subtotal` | Currency | Total after item-level discounts and before the order discount. |
| `order_discount_pct` | Number | Order-level percentage discount, from 0 to 100. |
| `order_discount_amount` | Currency | Calculated value of the order-level discount. |
| `total` | Currency | Final order total. No VAT is added. |
| `order_status` | Text/dropdown | Starts as `Open`; owner may change it to `Delivered` or `Cancelled`. |
| `email_status` | Text/dropdown | Starts as `Pending`; Apps Script changes it to `Sent` or `Failed`. |
| `email_sent_at` | Date/time | Time the email request succeeds; blank until then. |
| `email_error` | Text | Short operational error when sending fails; blank after success. |

`order_status` is a fulfilment field edited by the owner. `email_status` is an
operational field controlled by Apps Script and does not indicate whether a
message landed in the recipient's inbox rather than spam.

## `Order Items` schema

| Column | Sheet type | Purpose |
| --- | --- | --- |
| `order_ref` | Text | Links the line to its row in `Orders`. |
| `line_number` | Number | Stable display order starting at 1. |
| `product_id` | Text | ID from the authoritative product tab. |
| `product_name` | Text | Product-name snapshot at the time of ordering. |
| `category` | Text | Category snapshot for future filtering/reporting. |
| `unit` | Text | Unit snapshot, such as `case`, `pack`, or `unit`. |
| `quantity` | Number | Positive whole-number quantity. |
| `unit_price` | Currency | Product-price snapshot loaded by Apps Script. |
| `discount_mode` | Text | Blank, `pct`, or `fixed`. Fixed discounts apply per unit. |
| `discount_value` | Number/currency | Original percentage or fixed-per-unit value entered by the salesperson. |
| `discount_amount` | Currency | Total item discount across the line quantity. |
| `gross_line_total` | Currency | `quantity × unit_price` before the item discount. |
| `line_total` | Currency | Final line total after the item discount. |

Names, categories, units, and prices are stored as snapshots. Editing a product
later must not change the historical meaning or total of an existing order.

## Frontend request contract

The frontend will eventually send a JSON body to the deployed Apps Script web
app with `POST`. It sends product IDs and instructions, not trusted product
names, prices, calculated totals, recipients, order references, or statuses.

```json
{
  "contractVersion": 1,
  "submissionId": "1cb71ba7-9f21-4cd3-8587-3d58fa12a905",
  "customer": {
    "shopName": "Corner Shop Ltd",
    "contactName": "John Smith",
    "phone": "07700 900123",
    "email": "orders@cornershop.example",
    "notes": "Please deliver before 10am"
  },
  "items": [
    {
      "productId": "1",
      "quantity": 3,
      "discount": {
        "mode": "pct",
        "value": 10
      }
    },
    {
      "productId": "5",
      "quantity": 1,
      "discount": null
    }
  ],
  "orderDiscountPct": 5
}
```

The owner recipient is configured only in Apps Script. The endpoint must ignore
or reject any client-supplied recipient field so that it cannot become an open
email relay.

## Server validation and calculation rules

Before saving, Apps Script will:

1. Require `contractVersion: 1` and a valid `submissionId` UUID.
2. Require shop name, contact name, valid UK phone number, and valid email.
3. Require at least one order item.
4. Require unique product IDs and positive whole-number quantities.
5. Reload the existing product tab and match every requested product ID.
6. Reject missing, inactive, duplicated, or invalid catalogue products.
7. Load product name, category, unit, and price from the Sheet rather than the browser.
8. Permit percentage item discounts from 0–100.
9. Permit fixed item discounts from 0 up to the authoritative unit price.
10. Permit an order percentage discount from 0–100.
11. Calculate financial values in integer pennies and store GBP values to two decimal places.
12. Add no VAT, delivery charge, stock reservation, or minimum-order rule.

## Order and duplicate rules

- Apps Script, not the browser, generates the permanent `order_ref`.
- References keep the existing `ORD-YYYYMMDD-XXXXX` format.
- Reference generation and duplicate checks run under an Apps Script lock.
- `submission_id` is the idempotency key: only one order can exist for a value.
- Retrying a previously saved submission returns the existing order reference.
- A duplicate retry does not append rows or automatically send a second email.
- A different submission ID creates a different order even when its contents match.

## Save and email sequence

The backend workflow will be implemented in this order:

1. Parse and validate the request.
2. Acquire a lock and check `submission_id` for an existing order.
3. Load authoritative products and calculate the order.
4. Append one `Orders` row with `Open` / `Pending` statuses.
5. Append all matching `Order Items` rows.
6. Release the save lock.
7. Generate a PDF from the saved authoritative order data.
8. Send the PDF to `riotraders87@gmail.com` using Apps Script Mail service.
9. Update the saved row to `Sent` with `email_sent_at`, or `Failed` with `email_error`.
10. Return the permanent result to the frontend.

Saving is the acceptance boundary. If PDF generation or email delivery fails,
the order remains saved and the frontend must report that the order was accepted
but its email failed.

## Response contract

### Saved and emailed

```json
{
  "ok": true,
  "saved": true,
  "duplicate": false,
  "orderRef": "ORD-20260802-A4F2Q",
  "createdAt": "2026-08-02T14:30:00+01:00",
  "orderStatus": "Open",
  "emailStatus": "Sent",
  "totals": {
    "currency": "GBP",
    "grossSubtotal": 42.99,
    "itemDiscountAmount": 3.00,
    "subtotal": 39.99,
    "orderDiscountAmount": 2.00,
    "total": 37.99
  }
}
```

### Saved but email failed

```json
{
  "ok": true,
  "saved": true,
  "duplicate": false,
  "orderRef": "ORD-20260802-A4F2Q",
  "orderStatus": "Open",
  "emailStatus": "Failed",
  "message": "The order was saved, but its email could not be sent."
}
```

### Duplicate retry

```json
{
  "ok": true,
  "saved": true,
  "duplicate": true,
  "orderRef": "ORD-20260802-A4F2Q",
  "orderStatus": "Open",
  "emailStatus": "Sent"
}
```

### Rejected before saving

```json
{
  "ok": false,
  "saved": false,
  "code": "PRODUCT_NOT_FOUND",
  "message": "One or more products are no longer available. Refresh the catalogue and review the order."
}
```

Expected public error codes are `INVALID_REQUEST`, `INVALID_CUSTOMER`,
`INVALID_ITEM`, `PRODUCT_NOT_FOUND`, `PRODUCT_INACTIVE`, `INVALID_DISCOUNT`,
`CATALOGUE_UNAVAILABLE`, and `INTERNAL_ERROR`. Internal exception details must
be logged in Apps Script rather than returned to the browser.

## Explicitly out of scope

- VAT calculation or VAT columns
- Customer confirmation emails
- PDF storage in Google Drive
- Stock reservation or automatic stock deduction
- Delivery charges, minimum-order rules, or payment processing
- Customer accounts, authentication roles, or an admin dashboard
- Replacing the existing product-management workflow

These can be added later without changing the fundamental one-order/many-items
structure or the `submission_id` duplicate-protection rule.

## Phase 1 acceptance criteria

- Business decisions and exclusions are recorded unambiguously.
- Every permanent Sheet column has one defined meaning.
- The browser sends no authoritative commercial values.
- The owner email is fixed server-side.
- Duplicate and partial-success behaviour is defined.
- The next phase can implement Apps Script without inventing new business rules.
